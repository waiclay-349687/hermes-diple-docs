# 0015 文档版：标注先是草稿，任何点击都不挪动文档

日期：2026-10-29｜状态：已采纳｜范围：圈批·文档（diple-docs）；聊天版不变

## 背景

用户报了两个问题（任务单 V3-D3）：编辑浮层开着、没写字时，再选一段点「标注」，文档跳回顶部；只是选中、什么都没写，清单里就已经多了一条。还要求把所有能点的地方体检一遍。

## 决定

1. **根因以实测为准**。沙箱里给文档滚动容器（`.er-docwrap`）挂 `scroll` 监听，并包住 `focus`、`scrollIntoView`、`scrollTo` 和 `scrollTop` 的赋值，抓到的是 `CommentEditor` 挂载时调用的 `ref.current.focus()`。这个调用没有带 `preventScroll`，而当时浮层还没量好位置，停在滚动空间的 (0,0)，浏览器为了让输入框可见，就把面板滚到了 0。编排者最初怀疑「清单是 sticky 的」，实测不成立：清单并不在这个滚动容器里。
2. **聚焦一律不许滚动**。diple-docs 和 desktop-kit 里每一处 `focus()` 都带 `{ preventScroll: true }`。清单里的卡片要进入视野时，只滚 `.er-items` 自身（`focusInList`），不用 `scrollIntoView`，因为它会连带滚动外层所有容器。浮层量好位置之前设为 `visibility: hidden`，这时它拿不到焦点。另加一条源码扫描单测（`v3d3-focus-guard`）做守卫，白名单目前为空；以后确实需要滚动的聚焦，要写进白名单并注明理由。
3. **标注先是草稿**。草稿只存在于页面的 state 里（`page.jsx` 的 `draft`），不是一条 item：
   - 不发任何请求，不进清单，不上页边状态条，所选原文用 `er-draft` 高亮标出来（和当前条同一种底纹）；
   - 文件刷新照旧暂缓（`CommentEditor` 在挂载时 hold）；
   - 点「保存」（或回车）才调一次 `store.add(range, words)`，意见随这一次请求一起写入：没写字就存成划线，写了字就存成批注。之后它成为当前条。「保存并发送」先保存，再发送这一条。
   - `CommentEditor` 新增 `commit` 参数，传了就走草稿逻辑：失焦不保存（点外面由浮层判断怎么处理），每个草稿只写一次，之后发送前再 flush 也不会重复写。
   - 放弃的规则照聊天版（ADR 0010/0011 一带的设计第 2.4 节）：Esc 和 × 丢弃草稿；点浮层外面时，空草稿丢弃，有字的草稿晃一下并保留，拖选文字不算点外面；浮层开着时又在别处点「标注」，空草稿直接换成新的，有字的晃一下并保留。
   - 已经标注过的原文（原文相同、行号相同，和后端的判重规则一致；`store.anchorFor` 在本地就能算出来）直接打开已有的那一条，不新建。
   - 「替换原文」用在草稿上时，只改草稿里的原文，已写的字保留；横幅上点取消，草稿原样恢复。
4. **布局变化不挪阅读位置**。收起或展开清单、折叠底栏、用拖拽手柄改宽度时，文档会因为宽度变化重新换行。这时 `scrollTop` 虽然没变，眼前的内容却可能挪走好几百像素。现在在变化发生前记下面板顶部的第一个块，布局完成后（这一次布局和下一帧各做一次）把它放回原来的屏幕位置。只在变化发生时读取布局，滚动时不读（沿用 V2.1 的规则）。
5. **点击矩阵**写进设计文档第十一节。`tests/e2e/v3d3-matrix.mjs` 逐行真点，检查滚动、条目数、焦点、控制台报错和写入次数。写入次数按库里的效果计：新增或删除各算一次，每次编辑会让 mutation 加一。之所以不直接数请求，是因为 contextBridge 暴露的桥接对象改不了，没法在页面里拦截。聊天版做精简版（`v3d3-chat.mjs`），全部通过，所以聊天版不改。

## 后果

- 选中文字但没保存，就不会在清单、数据库或任何其他地方留下痕迹。刚选完还没保存时，页面上没有序号（浮层头部显示「+」）。
- 「重复标注」的提示条（`review.duplicate`）不再出现，改为直接打开已有的那一条。
- 测试里原来「⌘⇧E 之后马上 POST」的断言，改成「保存之后才 POST」（`review.test.mjs` S48–S50、XR-05）。

## 补充（R11-F，2026-10-29）：草稿有自己的生命周期，复制给 AI 不依赖圈批

范围同上；聊天版只改了测试脚本。上面第 3 条「放弃的规则」由下面第 1、5 条取代。

### 背景

第 11 轮交叉审查用反例证明 ADR 0015 的草稿只在「点浮层外面」「再标注别处」两条路上守住了：点卡片、「编辑意见」、页边刻度等入口会把有字的草稿藏起来却留着底纹；文件刷新后草稿的位置不跟着走；保存请求未返回时继续打字会丢字；另一个窗口已保存同一段时会被静默覆盖；关页面就丢。另外「复制给 AI」被圈批的状态和有没有会话连带禁用了。

### 决定

1. **所有切换编辑目标的入口经过同一个守卫** `holdDraft()`：有字的草稿 → 不切换，浮层回到眼前并晃一下；空草稿 → 丢弃再切换。不变式：草稿在（且不在「重新选取原文」中）就一定有浮层；底纹只随浮层画。
2. **草稿是一个有锚点和版本的对象**：`{ range, anchor, doc, lost, restored, collision }`。草稿活着就 hold 文件刷新，生命周期归草稿，不归 textarea。只有「刷新」会在草稿开着时换文本，这时用 `Anchor.locate` 重新定位：唯一 → 跟过去；找不到或有歧义 → 字保留，「保存」不可用，直到重新选取或放弃。
3. **草稿会话 + 操作票据（R11-H，取代 `seq` / 共享的 `draftSaved`）**：会话有不变的 `draftId`、每次重选/定位递增的 `anchorVersion`、每次输入递增的 `textVersion`。所有保存、保存并发送、冲突选择均同步领取不可变票据 `{draftId, anchorVersion, textVersion, intent}`。回包与当前会话的身份或锚点版本不符，只由 store 把条目落进清单；不关闭、不发送、不清缓存、不切编辑对象。相符时，仅 `intent === 'send'` 才发送，而且只用本次回包的 id，不再从可变 ref 取 id。输入框不锁，保存期间续写转成该条目的未提交修改，见第 5 条。发送不 flush 续写的新字。
   - **一把锁**：保存、保存并发送及三种冲突选择共享按 draftId 的同步锁，`finally` 释放；在途期间这些按钮和「重新选取原文」全部禁用，显示「正在保存…」。Esc / × 仍可明确放弃，之后的旧回包没有界面副作用。
4. **冲突由用户选**：同一段在别处已保存且意见不同，浮层里显示冲突条（对方的意见在上，我的草稿在框里），「保留已有 / 用我的替换 / 合并」，选了才写；对方是划线时直接把我的字写上去；我这边是空草稿时打开已有那条并提示。
5. **缓存按文件、按 draftId 分槽**：`draft:<path> = {v:2, slots:{[draftId]:slot}}`，兼容旧单槽格式，不进数据库。草稿槽保留锚点、文字和两种版本；成功保存仅 compare-and-clear 票据对应且版本一致的槽。恢复条仅操作它自己的槽，「重新选取原文」先经过 `holdDraft()`，不能覆盖另一份写了字的草稿。
   - **续写跨重开**：保存成功但用户已续写，槽转为 `{kind:'pending-edit', draftId, itemId, baseMutation, text}`；按 itemId 恢复编辑，提示「恢复了未保存的修改」。真正 PATCH 成功且没有更晚输入才清槽；新输入继续留存，明确 Esc / × 才放弃。基础 mutation 一并恢复，别的窗口改过时仍显示冲突，不静默覆盖。
   - 关闭/重载不会清缓存，空新草稿不缓存；显式放弃只删除自己的槽。README 说法仍为：**Esc 或 × 才丢弃；点外面、切到别的条目、关闭或重载都不会丢**。
6. **复制给 AI 是本地动作**：菜单的打开不再看圈批状态和会话；只按目标禁用（发送目标看圈批状态、发送中、范围里有没有可发的；复制只看范围里有没有条目）。
7. **点击矩阵由机器核对**：控件清单是数据（`tests/desktop/v3d3-controls.mjs`），每个控件区分可用 / 禁用状态；e2e 记账，`audit()` 判定：没跑到 = FAIL，SKIP 单独计数且不算通过，只有 T3（会在宿主打开访达）是手动。写入次数改由后端请求日志核对：`DIPLE_DOCS_JOURNAL=1`（只在沙箱设置）时 `GET /debug/journal` 返回每个非 GET 请求；平时这个路由是 404，什么都不记。

### 后果

- 守卫让「点卡片」在有字草稿时什么都不做（只晃）；这是有意的：草稿必须先保存或放弃。
- 草稿开着时文件刷新仍然暂缓（和上面第 3 条一样），但「重新选取原文」期间也暂缓了。
- 后端多一个只读调试路由；默认关闭。
- 聊天版没有产品改动；`v3d3-chat.mjs` 改为逐项选择发送菜单、先「全部清空」再发送、真点「回到输入框」。

## 补充（R11-J，2026-10-29）：冲突选择所见即所得，保存成功只有一个出口

第二次复审（R11c）证明：冲突里选「合并」后在途续写，pending-edit 只记了「我的草稿 + 续写」，下一次保存（CAS 正常）把对方意见删掉了（XR11c-01）；已存条目「文字没变」「远端已是同样的字」两条提前成功的分支只关浮层、不清槽，重开反复提示「恢复了未保存的修改」（XR11c-03）。

### 决定

1. **冲突选择所见即所得**（取代上文第 4 条「选了才写」里写入文本的来源）：点下按钮的那一刻，先把浮层输入框换成将要写入的全文、光标放到末尾，再发 PATCH。合并 = 对方意见 + 空行 + 我的草稿；用我的替换 = 我的草稿；保留已有 = 对方意见，转为编辑已有那一条（不写）。换字是一次程序修改（`textVersion` +1、缓存槽跟着写），票据在换字**之后**领取。
   - **不变量**：任何一次提交，回包到达时的基线就是当时发出去的那份全文；在途续写是相对这个基线的修改，pending-edit 记录的永远是「基线 + 续写」，不会少掉对方那段。
   - 409 或失败且没有续写：框回到我的草稿，冲突条留着（409 时换成对方最新意见与 mutation），再选不会把对方意见叠两遍；有续写：框里的字原样保留。
2. **保存成功只有一个出口**：已存条目的编辑框（含 pending-edit）凡语义上算成功——真正写入、文字没变、409 后对方恰好存了相同的字——都走 `CommentEditor` 的 `succeed()`：更新基线 → `onSaved`（页面按 `textVersion` compare-and-clear 槽位）→ 没有在途续写才关浮层。不再有「提前 onDone、不清槽」的分支。草稿那一侧的成功仍只经 `landDraft()`。
3. **枚举补缺**：测试的 fake backend 按 API 约定检查 `expectMutation`（409 `detail:'stale'`）并可注入 reject；交错枚举的 `settle()` 增加「逐个释放、每个单独 flush」模式；新增三步序列（冲突选择在途→续写→保存 ok/409/reject；首次保存在途→续写→关闭重开，回包在关前/关后/重开后；恢复的 pending-edit→保存遇 409/reject→重试）与跨文件 A/B 交错；断言同时保全对方已有的字（`tests/desktop/v3d3-r11c-draft.test.mjs`、`v3d3-r11b-draft.test.mjs`）。

### 后果

- 「合并」后框里多了对方的字，用户可以直接删改；发出去的就是框里看到的。
- 关闭期间第一次保存才落库、重开后再保存，会把自己刚存的那条当成冲突（字不丢，选「用我的替换」即可）；这是既有行为，本轮只用测试锁住结果，没有改。
